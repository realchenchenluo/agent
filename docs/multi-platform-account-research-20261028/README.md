# 多场景、多平台、一个账户管控：GitHub 调研与落地建议

日期：2026-10-28

## 结论先说

这个方向可以做，而且适合我们现在的产品定位：用户只需要面对一个账户和一个对话入口，系统把基金、银行卡、日常支出、订阅、账单和模拟任务统一整理，再由 Core Agent 判断应该调用哪个场景。

GitHub 上没有一个项目可以直接复制进现有 Cloudflare Worker 后就完成全部需求。比较稳妥的做法是：保留现在的 Core Agent、Memory、Risk、审批、审计和模拟执行链路，只吸收成熟项目里的账户归集、账单清洗、市场数据工具和权限设计，作为独立适配层接入。

当前集成页：<https://personal-ai-fund-chat.ai-banking-agent.workers.dev/>

本次检查结果：页面可访问，`/health` 返回正常，当前服务仍是分析/模拟模式，`execution_allowed=false`。因此它已经是安全的统一入口，但现阶段主要覆盖持仓核对，还不是完整的多平台账户中心。

## 最适合我们的组合

### 1. Core Agent 继续做总入口

用户只看到一个账户和一个对话框，例如：

> “我这个月工资到账了，想拿 8,000 元买基金，但下个月要交房租和信用卡账单，能不能买？”

Core Agent 负责识别这是“收入 + 生活支出 + 投资计划”的跨场景问题，然后把统一任务交给对应模块。Core 不重复计算 Quant，不修改 Memory 规则，也不能绕过 Risk。

### 2. 增加账户归集层

建立统一的账户目录，把不同来源先登记成同一种格式：

- 银行账户：余额、待到账、待付款；
- 基金/证券账户：持仓、成本、估值、收益；
- 信用卡和支付账户：账单日、还款日、待还金额；
- 生活账本：房租、学费、订阅、日常消费；
- 用户上传的截图、CSV 或 OFX：作为待确认数据，不能直接当成已确认事实。

每条数据都保留来源、时间、确认状态和所属账户。这样用户只绑定一次，后续查询、预算、风险提醒和模拟任务都能使用同一份数据。

### 3. 金融数据工具只读接入

可以参考 FinanceMCP 的工具拆分，把行情、基金资料、新闻和历史数据作为只读工具接入。工具返回的数据必须带来源和时间，Core 只能引用结果，不能把外部数据直接写成用户资产，也不能因为行情工具失败就编造结果。

### 4. 大模型放在服务端网关后面

目前代码已经有统一模型网关和供应商适配层。后续可以在服务端配置 DeepSeek、通义千问或 OpenAI 兼容接口，浏览器只调用我们的 Core API，不接触 API Key。

模型只负责理解用户话语、拆分任务和生成解释；持仓收益、资金缺口、预算、Risk 判定、审批状态和模拟执行结果仍由确定性模块完成。模型超时、429、余额不足或返回格式错误时，任务必须进入失败或待处理状态，不能假装成功。

## 推荐的统一流程

```text
用户登录
  ↓
一个账户绑定多个资金来源
  ↓
统一对话入口
  ↓
Core Agent 识别意图并生成任务
  ↓
Memory 提供已确认的用户约束
  ↓
金融工具读取外部信息（带来源）
  ↓
确定性计算整理资金缺口与冲突
  ↓
Risk 进行权限、额度、用途和参数检查
  ↓
无需资金动作：直接回答
需要资金动作：人工审批
  ↓
只允许模拟执行 / PAPER 执行
  ↓
任务、审批、Risk 结果和审计记录使用同一个 task_id
```

## 先做哪些功能

### 第一阶段：能看清楚

1. 一个账户下展示所有已接入的资金来源；
2. 展示总资产、可用资金、未来 30 天必须支付的钱；
3. 自动区分“已经确认”“用户上传但未确认”“外部数据”；
4. 用户点击一笔数据，可以看到来源、时间和计算过程；
5. 统一对话可以同时问基金、账单和生活支出。

### 第二阶段：能发现冲突

1. 识别投资计划和房租、学费、信用卡还款的时间冲突；
2. 明确显示“缺口是多少”“哪笔钱不能动”“调整后会怎样”；
3. 给出减额、延期或保留现金的建议；
4. 用户确认后才把约束写入 Memory；
5. 风险提醒带原因和来源，不只显示一个红色等级。

### 第三阶段：能跟进完成

1. 生成待办任务和到期提醒；
2. 需要资金动作时先进入审批；
3. 审批通过后重新检查金额、收款方、用途和当前余额；
4. 参数变化、签名不对、服务未接通或 Risk 拒绝时停止执行；
5. 所有结果都能按 `task_id` 查到完整记录。

## 不能直接套用的部分

- 不能把第三方项目的银行登录、支付授权或交易执行直接接进比赛演示；
- 不能把模型的自然语言回答当成账户事实或执行回执；
- 不能把外部行情项目的结果直接当作投资建议；
- 不能因为项目写着“agent”就跳过我们已有的 Risk、人工审批和审计链路；
- AGPL 项目不能未经评估就复制到我们的交付代码中；
- 多个平台的真实 API、数据授权、额度和合规范围还需要分别确认。

## 建议的下一步

1. 先在现有页面增加“账户总览”和“来源标记”，不改动现有持仓核对流程；
2. 从 MIT 的 `open-finance` 思路整理账户、账单和权限字段；
3. 把 FinanceMCP 或其他金融数据源封装为只读工具，先用合成数据验收；
4. 用现有模型网关接入一个外部模型，先做 staging，设置小额或零费用测试边界；
5. 通过三条验收案例：投资与房租冲突、信用卡到期提醒、模型失败后任务停止；
6. 验收通过后，再把新模块接入当前公开页面。

本次调研只形成方案和候选清单，没有复制第三方代码，也没有修改现有线上页面。
